[eThang Agent](https://github.com/eglove/ethang-agent) is an AI agent harness for Windows: the scaffolding an AI model acts through — agent loop, tool dispatch, session persistence, desktop UI — while the model supplies the decisions. It is built on .NET 10 with an Avalonia frontend, and it talks to [OpenRouter](https://openrouter.ai/) and [z.ai](https://z.ai/) behind provider-neutral contracts. This post is a breakdown of how the application is put together: the project architecture, the tool surface, the provider layer, the persistence model, and the test strategy.

The design bet is simple to state. The model is the easy part; the harness is where reliability is actually decided. A hung tool call, a lost session, a corrupted transcript — none of those are model failures, and all of them are harness failures. Everything below follows from treating that seriously.

## Architecture: one project per bounded context

The solution is organized as one project per bounded context, plus a set of anti-corruption layers (ACLs) that isolate every external dependency behind its own boundary:

- **Domains** — `eThangAgent.Tool.Domain` (tool contracts), `eThangAgent.Conversation.Domain` (turns and streaming), `eThangAgent.Agent.Domain` (the agent loop), `eThangAgent.Model.Domain`, `eThangAgent.Capability.Domain` (the capability registry), `eThangAgent.Memory.Domain`, `eThangAgent.Skill.Domain`, `eThangAgent.State.Domain`, and `eThangAgent.SharedKernel` for shared primitives like `Result<T>`.
- **ACLs** — `eThangAgent.Roslyn.ACL` (script execution), `eThangAgent.OpenRouter.ACL` and `eThangAgent.Zai.ACL` (providers), `eThangAgent.Provider.Wire` (wire-format contracts), `eThangAgent.FileSystem.ACL`, and `eThangAgent.Storage.ACL` (SQLite).
- **Composition and UI** — `eThangAgent.Composition` is the host-agnostic wiring used by `eThangAgent.Desktop`, the Avalonia frontend.

Domains do not know Roslyn, HTTP, OpenRouter, or SQLite exist. Each external concern sits behind an interface owned by the domain and implemented by an ACL, which is a textbook anti-corruption layer arrangement. The rule buys something concrete: the tool-contract tests run without compiling a single script, and swapping the OpenRouter ACL for a local mock never touches the conversation logic.

## The tool layer: validated contracts plus one general tool

The harness exposes discrete tools — read, write, edit, search, git_status, working_diff, db_schema, db_query, todo, curated memory, clarify, sub-agent spawning — and each one is a class implementing a single `ITool` interface with a declarative `ToolDefinition`: name, description, typed parameters, required-parameter list. Alongside them runs `exec`, a general-purpose C# scripting tool that compiles and runs a program in-process through Roslyn.

Every tool follows the same shape. Parse the input into a validated value; on failure, return a typed error. Only then check the budget and run. From `ExecTool.cs`:

```csharp
Result<ExecToolInput> parsed = ExecToolInput.Create(input.JsonArguments);
if (!parsed.IsSuccess)
{
  return Task.FromResult(new ToolResult(
      $"Error [{parsed.Error.Code}]: {parsed.Error.Message}", true));
}

Result<ToolCallEnvelope> budget = ToolCallEnvelopeParser.Parse(input.Name, input.JsonArguments);
```

A malformed call never reaches the compiler; it comes back as `Error [Code]: message`, which the model can correct directly. Validation rules live in the parameter declarations themselves — `Minimum: 1` on a whole-number parameter is enforced by the envelope parser, not by a convention.

The budget deserves its own paragraph because it is the spine of the whole tool surface. Every tool call carries a mandatory `timeoutSeconds` (a whole number, 1–3600). When the budget elapses, the call fails as `Error [ToolTimeout]` — a stoppable, named error the model can recover from by re-issuing with a larger budget or taking a different route. Nothing hangs silently. The agent loop itself runs uncapped and honors cancellation at every turn boundary.

`WriteTool` shows the same philosophy at the file boundary: the call fails if the file exists unless overwrite is exactly true — it will never silently replace anything, and parent directories are never created automatically. The overwrite gate is a declared parameter, not prose in the docs:

```csharp
new ToolParameter("overwrite", ToolParameterType.Flag,
    "Optional. Defaults to refusing replacement of an existing file; true replaces it.")
```

In the desktop transcript, each call and result renders as an expandable card — arguments pretty-printed on the call, full result content on the result, errors highlighted red:

### Composition through exec

The named tools are also exposed inside the exec script environment, which makes them composable. One script can read a file, patch it, run the test suite, and conditionally commit — with branch logic no linear tool-call sequence can express:

```csharp
var head = Tools.read(new { path = "src/App.ts", startLine = 1, endLine = 50 });
Tools.edit(new { path = "src/App.ts", old = "render()", replacement = "renderApp()", occurrences = 1 });
var tests = Shell("dotnet", "test");
if (tests.ExitCode == 0)
  Tools.Invoke("git_commit", new { type = "fix", description = "mount App once" });
```

`Shell` here is the exec environment's escape hatch to native processes: no shell intermediary, each argument one token of a native command line re-parsed with Windows argv rules, exit code propagated verbatim. Large outputs are never silently truncated — past 50,000 characters, both ends are preserved and the full text is written to an artifact file the model can read back.

## The provider layer

Provider access is split into two ACLs behind a shared wire-contract project. Each agent tab binds to exactly one provider — [OpenRouter](https://openrouter.ai/) or [z.ai](https://z.ai/) — for its lifetime. The split is deliberate: the two providers differ in model catalogs, endpoint modes, and capability surfaces, and the harness refuses to paper over that with a merged abstraction.

A few behaviors worth stealing:

- **Retries with backoff** — 429/408/5xx, transport errors, and timeouts retry exponentially (four attempts by default), honoring a server `Retry-After` hint. A streaming request retries only while nothing has been emitted; mid-stream failures surface as errors so output is never duplicated.
- **Continuation** — when a response hits the model's output limit (`finish_reason: length`), the partial answer is kept, a continuation nudge is appended, and the loop resumes, bounded per turn. A stream cut off without its terminator is a `StreamInterrupted` error, never a silently truncated answer.
- **Capability honesty** — z.ai's web search, page reading, image generation, OCR, and transcription tools exist only on the endpoint that actually offers them. The harness does not simulate capability an endpoint lacks.
- **Context compaction** — the status bar shows live token utilization; when it crosses 80% at a turn boundary, the oldest conversation is summarized by a compaction model and replaced with that handoff. The session keeps going instead of dying at the window, and compacted sessions persist and resume like any other.

## Persistence and memory

The persistence design is easiest to see as its tables. The database groups cleanly along the same bounded-context lines as the code — one set of tables per context, with foreign keys reaching across:

<PostImage src={DbDiagram} alt="Diagram of the eThang Agent SQLite database, grouped by bounded context with foreign-key relationships between tables" caption="The app database: tables grouped by bounded context, foreign keys crossing where contexts meet." />

Everything lives in one app-owned SQLite database (`eThangAgent.Storage.ACL`, schema changes via versioned migrations): full transcripts including tool calls and results, durable workspace state keys, the curated-memory store, and the agent graph. Three consequences:

1. **Resume** — any session can be reopened from the Sessions menu and replayed in full, on its original provider and workspace, with history carried into the next turn.
2. **Recall** — `memory.recall` searches prior transcripts for decisions, errors, and context, so work from earlier sessions is retrievable rather than gone.
3. **Curation** — a separate versioned, tagged, full-text store holds durable facts (conventions, failed approaches), with turn-boundary nudges prompting the model to write things down.

API keys sit in the same database, DPAPI-encrypted with current-user scope — plaintext never touches disk, and only the Windows user who wrote them can read them back.

## Safety properties

Delegated power is rationed explicitly:

- The database tools are read-only on a read-only connection — writes, multiple statements, and `ATTACH`/`DETACH` are rejected.
- Sub-agents spawn with a hard depth limit and concurrency caps; children inherit the same tool ledger.
- Input typed mid-turn goes to a session inbox and reaches the model at the next safe point — never splitting a tool call from its results.
- Stop hard-cancels the turn and all of the session's sub-agents, and repairs half-finished tool batches in place so the transcript stays valid.
- `git_commit` validates messages against the user's chosen commit style and returns a typed error naming the violated rule.

## The test strategy

Tests mirror the architecture — the solution's 18 projects all have mirror-image test projects, xUnit v3 on Microsoft.Testing.Platform, in three tiers: domain unit tests use fakes only and never touch Roslyn, HTTP, or SQLite; integration tests exercise the real ACL implementations; E2E tests drive the desktop app headless against a local mock provider server shaped like OpenRouter and z.ai. Because external dependencies live behind ACLs, each tier tests exactly one boundary — which is the practical payoff of the architecture, not just its aesthetics.

## Where it is going

The public roadmap is ambitious. The desktop is headed toward a fullscreen IDE — by its own description inspired by JetBrains, not a chat box or an editor clone — with a file explorer with live syntax highlighting driven by a file watcher, a git view with realtime diffing plus PR and CI management, a static analysis view (duplicate code, dead code, code smells, security vulnerabilities) whose autofixes feed errors straight back to the agent, a realtime kanban view of agent plans and todos, a live database view, and a multi-window agent view for watching several runs stream at once. An AI debugging plan goes further: running projects on a debug port and analyzing internal state through the Debug Adapter Protocol, so the model reads program state instead of inferring it from stack traces.

Around the IDE: a background maintenance process that polls for hung or silently-stopped agents and restarts or reprompts them, with deadlock detection that kills the deadlock and reports back to the model. MCP support. Local model providers (LM Studio, Ollama) queried and listed like hosted ones. Agent-triggered compaction at milestones. Even formal methods: temporary TLA+ specifications written and checked to validate concurrency plans during the planning phase. And, remarkably for a planning document, subtraction: deleting the general file-search tool because in-process scripting covers it, deleting structured clarify prompts in favor of the model formatting its own questions.

## Wrap-up

The interesting engineering in an agent product is almost never the model. It is the budgets that keep a hung call from hanging a session, the contracts that make every failure recoverable, the persistence that makes every session resumable, and the architecture that makes all of it testable. [eThang Agent](https://github.com/eglove/ethang-agent) is a working, Windows-native take on that problem, and its repository is open if you want to pull on any of these threads.
